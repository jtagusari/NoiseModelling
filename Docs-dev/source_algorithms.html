Concepts & Overview — Road Emission Processing

The road emission processing pipeline converts traffic data (ROADS table) into acoustic emission data (LW_ROADS table) and subsequently into propagation-ready source points. This process is summarized as follows:

Step 1: ROADS table Creation

Detailed Period-Specific

SQL reads following fields:

  • Geometry: THE_GEOM (LineString with optional Z)
  • Primary Key: PK
  • Traffic Flow (per period D/E/N): LV_D, MV_D, HGV_D, WAV_D, WBV_D (vehicles/hour)
  • Speed (per period D/E/N): LV_SPD_D, MV_SPD_D, HGV_SPD_D, WAV_SPD_D, WBV_SPD_D (km/h)
  • Environmental (optional): PVMT, TEMP_D, TEMP_E, TEMP_N, TS_STUD, PM_STUD
  • Geometry (optional): JUNC_DIST, JUNC_TYPE, WAY, SLOPE
  • Legacy (backward compatibility): TV_D, HV_D (total/heavy vehicle counts)

Annual Average Flow (optional)

SQL reads following fields:

  • Geometry: THE_GEOM (LineString)
  • Primary Key: PK
  • Traffic: AADF or TMJA (annual average daily flow, vehicles/day)
  • Classification: CLAS_ADM (road category: 1=Motorway, 2=National, 3+=Local)

Process: Applies standard hourly distribution patterns (Berengier et al., 2019) to convert daily flow to period-specific emissions

Step 2: Emission Calculation

The emission generation process transforms road segment data with traffic parameters into sound power level tables suitable for acoustic propagation calculations. This section details the two-stage approach (ROADS → LW_ROADS).

The emission calculation transforms traffic parameters into sound power levels using the CNOSSOS-EU emission model:

Calculation Process:

  1. Parameter Extraction — traffic flow, speed, and environmental data are extracted from database records using cached field indices for performance
  2. Period-wise Calculation — sound power levels are computed independently for three time periods:
    • Day (D) — typically 06:00-18:00
    • Evening (E) — typically 18:00-22:00
    • Night (N) — typically 22:00-06:00
  3. Frequency Band Iteration — for each period, emissions are calculated across 8 octave bands:
    • 63, 125, 250, 500, 1000, 2000, 4000, 8000 Hz
  4. CNOSSOS-EU Evaluation — traffic parameters (vehicle counts, speeds, pavement type, temperature, etc.) are input to the CNOSSOS-EU calculation model, which applies empirically-derived coefficients (version 1=2015 or version 2=2020)
  5. Unit Conversion — calculated sound power in watts (W) is converted to decibels (dB) using standard acoustic formulas

Output Structure:

  • Dimensions: [3 periods] × [8 frequencies] = 24 emission values per road segment
  • Units: Sound power level in dB (decibels)
  • Format: Ready for insertion into LW_ROADS table columns (LWD63...LWD8000, LWE63...LWE8000, LWN63...LWN8000)

Step 3: LW_ROADS Table Creation

The calculated emission data is stored in the LW_ROADS table, which serves as the emission database for propagation calculations.

Table Structure:

  • 26 columns total: 1 PK + 1 geometry + 1 source type + 24 emission levels (3 periods × 8 frequencies)
  • Storage format: Relational database table with spatial indexing capabilities

Field Organization:

  • PK — Primary key copied from source ROADS table (maintains traceability)
  • THE_GEOM — Road segment geometry (LineString with Z coordinate)
  • EMISSION_TYPE — Source type identifier (default: 'ROAD', used for directivity calculations)
  • LWD63...LWD8000 — Day period sound power levels (dB) for 8 octave bands
  • LWE63...LWE8000 — Evening period sound power levels (dB) for 8 octave bands
  • LWN63...LWN8000 — Night period sound power levels (dB) for 8 octave bands

Database Operations:

  • Batch insertion — Emission records are inserted in batches (typically 100 records) for performance optimization
  • Geometry height assignment — All road segment vertices are assigned Z=0.05m via spatial SQL update operation (ST_UPDATEZ)
  • Primary key constraint — PK field is set as primary key after data insertion for referential integrity

Height Convention:
The fixed Z=0.05m represents the initial acoustic source height above ground level. This value undergoes coordinate transformation during propagation processing to maintain relative height above actual terrain or bridge surfaces.

Step 4: Geometry Loading

The geometry loading process queries the LW_ROADS table within a spatial calculation area (envelope) and prepares geometries for source point creation.

Spatial Query:

  • SQL pattern: SELECT * FROM LW_ROADS WHERE THE_GEOM && envelope
  • Spatial operator: && (bounding box intersection test) triggers automatic spatial index usage
  • Query optimization: Fetch size and forward-only cursor minimize memory consumption

Geometry Processing:

  1. Optional clipping — Road segments can be clipped to exact envelope boundary using geometric intersection
  2. Empty geometry filtering — Geometries that became empty after clipping are discarded
  3. Z coordinate validation — All vertices must have valid Z values (X, Y, Z); missing Z coordinates trigger immediate error
  4. Spatial indexing — PostgreSQL/H2GIS spatial indices ensure efficient retrieval for large datasets

Performance Characteristics:

  • Envelope-based filtering — Only sources within calculation area are loaded
  • Streaming results — Large result sets are processed incrementally
  • Early validation — Geometry issues are detected before propagation begins

Step 5: SourcePointInfo Creation

Loaded geometries are decomposed into individual source points with associated spatial and acoustic attributes.

LineString Segmentation:

  • Input: Road LineString geometry with multiple vertices
  • Process: Each consecutive vertex pair forms one source segment
  • Output: Array of source points, one per segment start position

SourcePointInfo Attributes:

  • sourceIndex — Sequential processing identifier for current calculation session
  • sourcePk — Database primary key from LW_ROADS (maintains link to emission data)
  • position — 3D coordinate (x, y, z=0.05m) representing segment start
  • li — Line segment length used for distributed line source power calculation
  • orientation — Direction vector derived from segment geometry, used for directivity adjustments
  • bridgeRelationship — Bridge mounting information:
    • bridgePkOn = -1 → no bridge (normal terrain source)
    • bridgePkOn ≥ 0 → source mounted on bridge (uses bridge deck as ground reference)

Emission Data Linkage:

  • JOIN operation: Source geometry table (LW_ROADS) is joined with emission data via primary key
  • Registration: Each source point is associated with its 24 emission levels (3 periods × 8 frequencies)
  • Retrieval mechanism: During propagation, emission levels are accessed via sourcePk lookup

Coordinate Validation:

  • Missing Z coordinates are replaced with default value (0.0)
  • All source points guaranteed to have valid 3D positions before propagation

Step 6: Propagation-Ready Source Points

SourcePointInfo objects are transformed into CutPointSource objects ready for acoustic propagation calculations through height coordinate conversion.

Height Coordinate System:

  • coordinate.z — Absolute Z position (0.05m from database)
  • zGround — Ground surface reference elevation
  • Relative height — Effective source height = coordinate.z - zGround

Conversion Process:

  1. Initial State:

    • coordinate.z = 0.05m (fixed value from LW_ROADS table)
    • zGround = 0.0m (initial estimate: coordinate.z - 0.05)

  2. DEM Integration:

    • Digital Elevation Model (DEM) provides terrain surface elevation
    • zGround is updated to actual ground surface height at source location
    • Enables accurate height-above-ground calculation regardless of terrain elevation

  3. Bridge Handling:

    • For sources on bridges (bridgePkOn ≥ 0):
      • Bridge deck height retrieved from Bridge database
      • zGround replaced with bridge deck elevation
    • Bridge deck becomes ground reference instead of terrain surface

  4. Relative Height Result:

    • Normal sources: 0.05m above DEM terrain surface
    • Bridge sources: 0.05m above bridge deck surface
    • Consistency: Same 0.05m relative height maintained in all scenarios

Design Rationale:

  • Separation of concerns: Absolute position (coordinate.z) and ground reference (zGround) stored independently
  • DEM independence: Fixed Z=0.05m works universally, independent of terrain elevation variations
  • Bridge compatibility: Unified height calculation framework handles both terrain and bridge surfaces
  • Flexibility: Ground reference can be updated dynamically without modifying source geometry
  • Acoustic validity: Ensures consistent 0.05m source height above ground reference for accurate propagation modeling

Output:
All road sources are now represented as CutPointSource objects with validated positions, emission data, and correct relative heights, ready for acoustic path construction and propagation calculations (see propagation_algorithms.md).
